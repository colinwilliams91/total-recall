# Recall Question Delivery — Architecture

## Overview

Total Recall generates recall questions asynchronously after every Git hook event. The question is synthesized by the AI provider and must reach the developer's terminal. This document describes the Phase 4A delivery paths and the plan for Phase 4B.

## Phase 4A Delivery (Current)

Phase 4A delivers questions where developers actually are, via two first-class paths:

```
git commit  →  pre-commit hook  →  POST /hooks/pre-commit  →  202 Accepted  (immediate)
                                                           ↓
                                                 goroutine: runPipeline(env)
                                                           ↓
                                        ExtractConcepts → cache.Save(env.Repo) → Synthesize(env.Repo)
                                                           ↓
                                           store.SaveQuestion(env.Repo, ...) (memory.db)
                                                    ↙         ↘
                                       mcpServer.ResourceUpdated   dispatcher (opt-in)
                                             ↓                         ↓
                                      MCP clients                  terminal.Adapter
                                    (recall_next tool)           (presentation.terminal: true)
                                             ↓
                                    GET /recall/next  ←  torec ask (post-commit hook)
```

### Path 1: MCP (primary, for AI agent harness users)

`mcp.NewStreamableHTTPHandler` is mounted at `/mcp/` on port 7331. AI coding agents (Claude Code, Copilot CLI) connected via MCP receive questions through the `recall_next` tool. After `Synthesize`, `runPipeline` calls `mcpServer.ResourceUpdated("recall://queue")` to notify subscribed clients.

**MCP surface:**
- `recall_next` tool — atomically dequeues one question (the `delivered` `question_events` row records `actor = "mcp"`; the store has no `claimed_by` column); `repo`/`branch` are optional pointers — absent or empty yields no dequeue (the store layer refuses empty scopes; no global pool exists)
- `recall_select` tool — records selection or `"skip"` (renamed from `recall_answer`; user-side field is `selected_index`); ID-keyed, optional `repo`/`branch` accepted for symmetry
- `recall_status` tool — daemon health, `ai_configured`, `queue_depth`; accepts optional `repo`/`branch` to scope depth
- `recall://queue` resource — subscribable; updated after each `SaveQuestion`; repo and branch derived from URI query string
- `recall://recent` resource — last 10 answered questions; repo and branch derived from URI query string
- `recall_workflow` prompt — system prompt instructing the agent to call `recall_next` (with repo and branch) after commits

### Path 2: Shell (`torec ask`, for terminal users)

A post-commit hook generated by `torec repo` calls `torec ask` after each successful commit. `torec ask` resolves the repo root via `git rev-parse --show-toplevel` and the branch via `git rev-parse --abbrev-ref HEAD`, sends both as `?repo=<path>&branch=<branch>` to scope dequeue, polls `GET /recall/next`, displays a "Thinking." animation, and renders the question interactively. When run outside a git repo (or on a detached HEAD) there is no branch context to scope to, so it exits with a stderr advisory — there is no global pool fallback.

```
GET /recall/next?repo=<path>&branch=<branch>  →  200 OK (question JSON) or 204 No Content
POST /recall/select?repo=<path>&branch=<branch>  →  {"ok":true,...}
```

Both REST endpoints use the same atomic `UPDATE ... RETURNING` dequeue as `recall_next`, scoped by `repo` and `branch`. SQLite's serialized writes guarantee exactly-once delivery per repo+branch scope (the Working Surface, per GLOSSARY.md).

`torec ask` is TTY-aware: if stdout is not an interactive terminal (CI/CD, piped output), it exits 0 silently.

### Unified backing store: `~/.tr/memory.db`

All persistent state lives in a single SQLite file. Both `concepts` and `questions` rows carry `repo` and `branch` columns tagging each row with the absolute repository path and branch it was generated from. This scopes recall questions to the work the developer is currently in — `torec ask` and MCP `recall_next` pass repo and branch so dequeue only surfaces questions from the active repo and branch. An empty `repo` or `branch` is refused at the store layer (there is no global pool). The `TR_HOME` env var redirects the entire data directory away from `~/.tr` for test/CI isolation. The full table set (`concept_registry`, `concepts`, `concept_aliases`, `questions`, `choices`, `selections`, `question_events`, `question_concepts`) is documented in `docs/ARCHITECTURE/CONCEPT_CACHE.md`.

## terminal.Adapter (opt-in)

`terminal.Adapter` is retained as an opt-in dispatcher for users who prefer the daemon-pane workflow:

```yaml
# ~/.tr/config.yaml
presentation:
  terminal: true  # enables terminal.Adapter dispatcher
```

When `presentation.terminal: false` (the default), the dispatcher is nil and questions are delivered only through MCP and REST.

## Phase 4C — Answer Feedback Loop (Current)

Phase 4A delivered questions to developers but stopped at `"✓ recorded"`. Phase 4C closes the loop: when a developer answers, the server evaluates correctness, persists the result, and (for terminal users) generates an AI explanation. The dormant `recall.Question.CorrectIndex` — computed and shuffled at synthesis time — is now stored at enqueue and used at answer time.

### Terminal path: `POST /recall/select?feedback=true`

```
POST /recall/select?feedback=true&repo=<path>&branch=<branch>
Body: {"id": 1, "selected_index": 0}

Server:
  1. GetQuestion(id) → StoredQuestion (with correct_index, choices)
  2. correct = choices[selected_index].IsCorrect
  3. correct_answer = question.choices[question.correct_index]
  4. recallEngine.GenerateFeedback(...) → feedback string (max 150 tokens)
  5. SubmitSelection(id, choice_id, feedback)
  6. Respond 200: {ok, correct, correct_index, correct_answer, feedback}
```

`?feedback=true` triggers the AI feedback call. Without it, the handler still evaluates correctness and persists the selection, but `feedback` is `null` in the response and the DB column is left NULL. Skip path (`{"id": 1, "skip": true}`) is identical to the old behaviour — no evaluation, no AI call. The legacy `answer_index` field is rejected with an explicit 400.

### MCP path: self-explanation

```
recall_next tool response: {id, question_type, question, choices}   (correct_index withheld)
recall_select tool:
  Input:  {"id": 1, "selected_index": 0, "skip": false}
  Output: {ok, correct, correct_index, correct_answer, feedback}    (feedback is null)
  Skip output: {ok, "skipped": true}
```

The MCP `recall_next` tool withholds `correct_index` — the agent drives the user's reflection, not its own answer key. `recall_select` evaluates server-side (for the atomic DB write) but does NOT call the AI for feedback — the agent is expected to explain using its own knowledge, per the `recall_workflow` prompt; `feedback` rides the response as `null` so the submit-response shape is identical across surfaces.

### Information boundary

- `GET /recall/next` (terminal REST) — does NOT return `correct_index`. The terminal client cannot pre-evaluate; it submits an index and receives the verdict. This preserves the integrity of the quiz for terminal users.
- `recall_next` tool (MCP) — also withholds `correct_index`. An AI agent seeing the answer doesn't invalidate the quiz (it still drives human reflection), but the withheld key keeps the tool payload identical to the REST shape.
- `recall://recent` (MCP resource) — includes `correct_index` for completed rows. There is no integrity concern in exposing the answer after the fact.

### `torec ask` state machine

```
stateThinking  ──[question]──▶  stateQuestion
                                      │
                       ┌──────────────┼──────────────┐
                       │              │              │
                  [1-N] press    Enter (skip)   q / Esc
                       │              │              │
                       ▼              ▼              ▼
                stateFeedback    stateDone      stateDone
                "Evaluating..."     │              │
                       │       (skip msg)     (silent)
                       ▼
                stateDone  ────▶  exit alt-screen ────▶  print verdict + feedback
```

After the alt-screen closes, `askCmd.RunE` prints one of:
- `→ Question saved for later.` (skip)
- `✓ Correct.` + indented feedback paragraph (correct)
- `✗ The answer was: <correct_answer>` + indented feedback paragraph (incorrect)
- advisory (caught up / daemon unreachable) — printed verbatim
- nothing (q/Esc clean exit)

If the AI feedback call fails, the verdict still prints — `feedback` is empty and the indented paragraph is omitted. The answer is always recorded.

### Schema migration

Schema changes are manual: `cache.Open()` uses `CREATE TABLE IF NOT EXISTS` with no `ALTER TABLE` path, so after a schema-changing build the data directory's `memory.db` must be deleted (or `$TR_HOME/memory.db` for test isolation) before starting the daemon. See `docs/ARCHITECTURE/CONCEPT_CACHE.md` for the normalized table set.

## Canonical wire schema (issue #33)

The recall surfaces share one payload vocabulary: snake_case keys, integer ids, and the withheld-correctness rule above. This section is the reference for the canonical shapes and the deliberate divergences.

**Question delivery — identical across REST and MCP:**

```json
{"id": 1, "question_type": "multiple_choice", "question": "...", "choices": ["a", "b", "c", "d"]}
```

**Submit response — identical across REST and MCP** (REST adds live `feedback` when `?feedback=true`; MCP always sends `null` and the agent explains itself):

```json
{"ok": true, "correct": true, "correct_index": 2, "correct_answer": "...", "feedback": null}
```

REST skip response: `{"ok": true, "skipped": true}`; MCP skip response: the same.

**Deliberate divergences (do not "fix" by breaking the MCP v1 contract — the bet is recorded in [docs/adr/0005-mcp-v1-wire-contract.md](../adr/0005-mcp-v1-wire-contract.md)):**

| Divergence | REST | MCP | Rationale |
|---|---|---|---|
| Empty queue | `204 No Content` on `GET /recall/next` | `{"question": null}` text result | Each is the transport idiom; the MCP shape keeps tool outputs self-describing for agents |
| Errors | HTTP status + `{"error": "..."}` body | Tool error (protocol-level) | Same transport idiom |
| Status | `GET /health` → `{"status": "ok"}`; queue depth only via `GET /recall/stale` (repo) | `recall_status` composite: `{"daemon", "ai_configured", "queue_depth"}` (repo+branch) | MCP agents need one call; the CLI composes health + config + `/recall/stale` itself |
| Scope inputs | `repo`/`branch` are required query params | Optional pointers (absent → empty → no dequeue) | MCP tool schemas tolerate omitted fields; the store layer refuses empty scopes either way |
| `recall://recent` rows | no REST equivalent | `{id, question_type, status, question, choices, correct_index, selected_indices, feedback}` | Post-answer surface, MCP-only; `selected_indices` is already plural for a future multi-select question type |
| `recall://queue` preview rows | no REST equivalent | `next.choices` marshals raw `cache.Choice` (PascalCase keys, includes the answer key) | Pre-answer preview only; treat as an MCP-internal shape. If an external consumer needs it, stabilize it before the MCP v2 work (issue #68) |

Any future surface (VS Code extension, stats) should consume the canonical shapes above rather than minting new field names.
