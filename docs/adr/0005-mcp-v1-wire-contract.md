# MCP v1 recall tools are a frozen wire contract: one canonical submit shape, `feedback` always `null`, correctness withheld until submission

The recall surfaces grew three delivery vehicles in quick succession — the REST endpoints (`/recall/next`, `/recall/select`), the MCP tools (`recall_next`, `recall_select`, `recall_status`, resources), and the TUI (`torec ask`) — and each initially shaped its payloads slightly differently: the MCP submit response lacked the `feedback` field REST returned, the tool was named `recall_answer` while the REST route was `recall_select`, and the correctness key appeared in different fields at different times. Every integration (an AI coding agent's tool schema, a VS Code surface, a script) wires against one of these shapes, so each divergence is a place a future consumer breaks.

Decision: **the MCP v1 shapes are frozen and the REST payload is canonical.** The canonical question-delivery shape (`{id, question_type, question, choices}` with no correctness key) and submit-response shape (`{ok, correct, correct_index, correct_answer, feedback}`) are documented as the reference in [DELIVERY.md](../ARCHITECTURE/DELIVERY.md), MCP rides them exactly (submit response carries `"feedback": null`), and the remaining REST↔MCP divergences are deliberate transport idioms, enumerated in the doc's divergence table — not defects to be normalized. An agent that wants correctness evaluation does it agent-side after submission (it sees the key in the `recall_select` response); the daemon does not generate AI feedback for MCP callers. Renaming or reshaping any `recall_*` tool, adding a required field to a response, or letting MCP return live feedback is a breaking change reserved for the MCP v2 work (issue #68), with a migration story for external clients.

The trade-off is real: the rejected alternative was agent-local pre-evaluation — MCP returning the correctness key (or live feedback) at delivery so the agent could judge its own answer before submitting. That was the pre-`recall_select` behavior, and it leaked the answer key into any client that renders tool output verbatim, defeating the quiz. The chosen alternative costs one extra round-trip per question and forbids server-side feedback for agent users, bought for a shape that every consumer (REST script, MCP agent, TUI) can parse identically. "Correctness withheld at delivery, revealed post-submission" is also simply the honest model of what the store does — the delivery path physically cannot emit the key.

Decisions folded in: (1) `recall_answer` → `recall_select` rename with `selected_index` as the user-side field — the verb now matches the REST route and the noun matches what the caller does (selects a choice, may also select "skip"); (2) MCP submit response includes `"feedback": null` explicitly so every surface parses one shape — additive to the frozen contract, since previously-absent-field parsers see a harmless extra key; (3) the correctness key moves out of the delivery payload entirely — `recall_next` never returns `correct_index`, it appears only in the `recall_select` response; (4) skip responses are symmetric (`{"ok": true, "skipped": true}` on both REST and MCP) rather than a third shape.

Full design, the surface survey that produced it, and the remaining deliberate divergences: [DELIVERY.md wire-schema section](../ARCHITECTURE/DELIVERY.md).

## Consequences

- External MCP clients integrate against `recall_next`/`recall_select` names and these payload shapes with a stability guarantee; the schema-normalization work (issue #33) must not reshape them — additive fields only until MCP v2.
- MCP agent users never receive AI-generated feedback (`feedback` is always `null`); the agent explains the verdict itself from the revealed correctness data. A server-side feedback path for agents would be an MCP v2 feature, not a fix.
- The TUI's live-feedback behavior (REST `?feedback=true`) is unaffected; it is the surface where server-side feedback was always intended to exist.
- `recall://queue` preview rows remain a PascalCase MCP-internal shape and the status composite stays MCP-only; treat anyone depending on those as an MCP-v1 client too.
