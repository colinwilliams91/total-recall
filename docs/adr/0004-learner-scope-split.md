# Learner scope split: difficulty reads the Working Surface, weakness reads the user

The performance-adaptive resolver reads two windows of the same answered history, and they deliberately scope differently: the correctness-ratio window that tiers the difficulty is scoped to the current repo+branch (the Working Surface), while the per-concept weakness tallies that rank the focus set key on the user-scoped registry identity and span every surface. The asymmetry is surprising on first contact — "why does one query scope and the other not?" — and it is a real trade-off, not an oversight: the all-per-surface alternative (the difficulty persona per repo, tallies per branch) was on the table during the spec refresh.

Decision: **the learner is user-grained; the difficulty floor is surface-grained.** Concept identity is user-scoped by design (`concept-identity`: one identity per concept across repos; the DB is a single user's brain), so per-slug weakness evidence naturally aggregates across surfaces — and the synthesis feed can only ever reorder concepts already on the current surface's feed, so cross-surface weakness surfaces as re-ranking of work the user is already touching, never as injected out-of-surface content (the `concept-identity` mastery-is-second-class rule holds). Difficulty, by contrast, is calibrated on the Working Surface's answered window: a user's docs-repo winning streak must not silently escalate the difficulty of their work repo. The rejected universal-scope alternative (everything per repo+branch) starves both features for the primary user class — branch-hopping agent-heavy developers never accumulate per-branch history, so the tier rules and focus ranking would silently never engage. The rejected user-global alternative (both windows user-wide) was deferred rather than chosen: per-project difficulty personas remain a plausible future opt-in (tracked in GitHub issue #65), revisitable once real outcome data exists.

Decisions folded in: (1) `cache.LearnerStats` implements the split as read-time policy — one method, tier window filtered by repo+branch, tally window filtered only by recency; no write-side scoping changes and no schema change; (2) the focus ranking orders Working-Surface concepts first, cross-surface concepts fill leftover slots up to the cap; (3) `Synthesize` still drops any focus concept absent from the current feed, which is what makes the cross-surface read safe; (4) window/threshold constants stay package-private (20 / 5 / 0.92 / 0.50 / 3) — no config knob for the split until spike evidence demands one.

Full design, delta mechanics, and implementation tasks: [openspec change](../../openspec/changes/archive/2026-11-12-performance-adaptive-resolver/design.md).

## Consequences

- `LearnerStats` carries one dual-scope contract rather than two methods; readers see `Answered`/`Correct` (surface-scoped) and `Concepts` (user-scoped tallies) from a single call, and the resolver derives surface membership from the synthesis feed's slugs.
- Cold start is per-surface by construction: a brand-new repo or branch resolves from the commit-shape baseline until its own answered window fills, even when the user has deep history elsewhere — the price of keeping difficulty personas surface-local.
- The store's "no global pool" doctrine is untouched: every write remains repo+branch scoped; the split lives entirely in read-time filtering.
- A future per-project difficulty persona (issue #65) is a read-policy change to the tier window only; the user-wide weakness tallies and the identity layer need no rework.
- FEATURES.md's "weaknesses follow you across projects" phrasing and the `learner-performance` spec both lean on this ADR for the why; the spec records the WHAT.
