# Single prompt-asset policy: the multi-doc generality was a bluff

The drop-in slot was built name-keyed to serve *N* prompt assets, and the surrounding narrative sold plural futures: a "finite set of valid names", `inactive` files explained through asset-registry vocabulary, overrides framed as a per-domain customization feature with community sharing behind it (and, someday, a platform). Reviewing `assets/prompts/question-generation-policy.md` closely exposed that this was overdesign: the policy doc is canonical and tightly bound to the tool's purpose — it shapes pedagogy *framing* (retrieval over recognition, counterfactual debugging, good/bad prompt shapes) — while question *content* is structurally determined by the synthesis turn (the working diff and cached concepts). Its tunable surface is small; two users with the same policy get different quizzes from their different diffs. A second question-generation policy has nothing meaningful to vary, and community sharing of policy docs was a pipe dream: the feature support we'd built was a general mechanism narrating a plural world for a singular asset, and the narrative was what kept making the docs confusing — implementation and implied roadmap were at odds.

Decision: **there will never be multiple question-generation policies.** The customization feature stays, scoped to what's real: one shipped asset (`question-generation-policy`), one override slot, one active doc. `tr asset sync` and `tr asset reset` gain argument-free forms that resolve the sole shipped asset by enumeration — zero assets or several refuse with the inventory pointer, so the rule is future-proof by *discovery*, not by hardcoding a constant. `reset`'s batch-removal apparatus is deleted outright (`--all`, `--force`, TTY confirmation gates): it answered "which of several overrides?" for a world that cannot exist, and an undocumented destructive flag would be obedience debt. Named `<name>` arguments survive on both commands — reset's remains the permissive stray-file cleanup path; sync's carries the explicit-name cases (`--force` stays there: it guards hours of re-tuning from a silent overwrite, which is unrelated to multiplicity). Docs tell the singular truth (FEATURES.md walkthrough, "one policy. one file. `sync` names it."), while the canonical `prompt-asset-loading` spec deliberately keeps its name-parameterized mechanism language — specs describe how the loader works; they do not enshrine the product bet that no second asset is conceivable in prose that would go stale the moment the bet is revisited. The plural machinery already in the code (`LoadAll`, `EmbeddedNames`, `UnmanagedNames`, the `inactive` tag, the startup warning) is retained but reframed: with a single-slot world, a stray file is by definition a mis-drop, so slot hygiene (one `inactive` tag, one startup log line) is exactly what the machinery still honestly provides — and more likely, not less, since users will inevitably copy shared docs around.

Decisions folded in: (1) the multi-doc concept is stripped from all user-facing narrative — package doc comment, AGENTS.md, README, FEATURES.md — while the mechanism stays generic and dormant; (2) the canonical `cli-asset-commands` requirement replacement is expressed as REMOVED + ADDED blocks rather than MODIFIED, because OpenSpec refuses MODIFIED blocks that drop existing scenarios and scenario-level retirement is exactly what the batch machinery needs; (3) the Community policy-sharing section is deleted rather than hedged — the honest residue is one trust sentence (a shared doc deploys by copying over the slot file; review what you import), since deploy-by-copy still works even if the sharing *feature* never does; (4) scenario-level alignment required archiving `prompt-asset-observability` first so the canonical `cli-asset-commands` spec existed for the REMOVED blocks to header-match; (5) renames (asset, file, `tr policy` subcommand) were declined — quasi-breaking and the descriptive name is cheap insurance if a second asset ever materializes; (6) the ADR itself, not the specs, is where "there will never be multiple policies" is recorded — this document owns the product bet.

Full design, delta mechanics, and implementation tasks: [openspec change](../openspec/changes/single-policy-asset-ux/design.md).

## Consequences

- `tr asset sync` and `tr asset reset` are argument-free in the primary path; typing `question-generation-policy` anywhere user-facing is documented friction, and README/FEATURES.md no longer spell the asset name out.
- `reset --all` is removed — a called-out BREAKING surface; any hypothetical script must use single-file named resets.
- The slot-inventory vocabulary (`inactive`, unmanaged-file warning) persists as *hygiene for a directory that should hold exactly one file*, not as multi-asset support — stray files become more likely, not less, in a single-slot world.
- The canonical specs remain name-parameterized: mechanically, a second prompt asset remains buildable without spec rewrites; the product decision to never ship one lives here and in the docs, not in the capability contract.
- Version history, forks, and drafts of the policy doc live outside the data dir (git, `~/policies/`); the slot is a deployment target — the ADR codifies the framing that resolved the "confined to git versioning" objection.
